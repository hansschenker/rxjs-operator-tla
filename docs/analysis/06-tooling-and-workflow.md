# 06 · Tooling, limits and workflow

What was run, how to run it, how to read what the checkers say, and what

## 2. Running the checks

```
npm install
npm run check            # tla-ts
npm run check:tlc        # TLC
npm run check:trace      # tla-ts, printing each counterexample
```

`scripts/check.mjs` reads the manifest, runs each `(module, cfg)` pair, and
compares the checker's status with the expected one. A row is `ok` when the
outcome is the expected one, so the bug demonstrations count as `ok` when
they fail in the expected way. The script exits non-zero otherwise, which
makes it usable in CI.

For TLC it needs Java 11 or later and the jar. It looks for the jar in the
VS Code extension folder and falls back to `TLA2TOOLS_JAR`; `JAVA` names
the executable when `java` is not on the PATH. To run one spec by hand:

```
cd specs
java -cp path/to/tla2tools.jar tlc2.TLC -workers auto -config Flatten_switch.cfg Flatten.tla
npx tla-ts -config Flatten_switch.cfg Flatten.tla
```

Or open the `.tla` file in VS Code with the TLA+ extension and run "Check
model with TLC". TLC writes `*_TTrace_*.tla` helper modules next to the spec
after a violation; `.gitignore` excludes them and the script deletes them.

tla-ts mirrors TLC's exit codes: 0 on success, 12 for an invariant
violation, 13 for a liveness violation, and also 13 for a violated action
property. All three were observed in this session.

## 3. Reading the three kinds of counterexample

**An invariant violation** is a finite trace ending in the state that
breaks the predicate. Each state lists every variable, and each step names
the action. Read the last two states:

```
Error: Invariant NoInterleaving is violated.
State 5: <InnerNext>   out = <<<<2, 1>>>>
State 6: <InnerNext>   out = <<<<2, 1>>, <<1, 1>>>>
```

The violated invariant tells you *what* is wrong; the step that reached it
tells you *which action* is under-guarded. Here `InnerNext(1)` was still
enabled after inner 2 started: the `switch` strategy's cancellation is
missing.

**An action property violation** looks the same but the error names the
action property, and the offending step is the last one. TLC prints
`Action property X is violated`.

**A liveness violation** is a lasso: a finite prefix followed by a loop,
printed either as a `Stuttering` final state (the loop is "do nothing") or
as "Back to state N". The trace shows a behaviour in which the promised
thing never happens:

```
Error: Temporal property EventuallyTerminal was violated.
State 4: <AComplete>   aDone = "complete"
State 5: <BNext(y)>    b = <<y>>
State 6: <BNext(x)>    b = <<y, x>>
State 7: Stuttering
```

The question to ask of a liveness counterexample is "which action should
have been forced to happen here, and is it reasonable to assume it will?".
If yes, add fairness for it. If no, the property is false and the operator
needs a `timeout`, a `takeUntil` or a different design. In the trace above
the missing action is any step of source B, and assuming it is not
reasonable; that is the point of the demonstration.

## 4. From a trace to a marble test

A TLC trace of a time-based spec is a marble diagram with the frames made
explicit. The translation is mechanical:

1. Group states by `now`. Each group is one frame; each `Tick` step starts
   a new one.
2. Within a frame, write the source's values as letters on the input line
   and the operator's outputs on the output line, in trace order.
3. `SourceEnd("complete")` is `|`, `SourceEnd("error")` is `#`,
   `subscribed' = FALSE` (or `connected' = FALSE`) is `!` on the
   subscription line.

The guard-removal experiment from part 04 translates as:

```
TLC trace: Tick ×6 with outDone = "active" throughout, D = 5
marble:    source  -------      result  -------  (expected  -----|)
```

That is a `TestScheduler` test which fails against the broken operator and
passes against the fixed one. For non-timed specs the same works with each
step as one frame.

tla-ts returns the trace as a JavaScript object from its `check()` API, so
this translation can be a script rather than a manual step.

## 6. What the checker cannot tell you

**It checks the model, not the operator.** Every spec here is a claim about
what `take`, `switchMap` or `debounceTime` does, written from the
documentation and the RxJS 7 source. If the claim is wrong, TLC verifies the
wrong thing. The gap is closed by running the same invariants as
property-based tests against the real operator: generate a marble diagram,
run it through `TestScheduler`, and assert the spec's invariants on the
result. In TypeScript with `fast-check` and the RxJS testing utilities, a
`take(N)` conformance test is roughly:

```ts
fc.assert(fc.property(marbleArb, (marble) => {
  const { out, outDone, subscription } = run(marble, take(N));
  return out.length <= N                          // AtMostN
      && isPrefix(out, inputValues(marble))       // OutIsPrefixOfIn
      && (out.length < N || outDone === 'complete')   // CompletesAtN
      && (!isTerminal(outDone) || subscription.ended); // UnsubscribedWhenDone
}));
```

Each operator needs this once. After that, the TLA+ spec is trusted for
pipeline-level reasoning and the property test keeps it honest across RxJS
versions.

**It checks within bounds.** Two values, streams of length four, six frames.
Most design bugs appear at these sizes; a bug that needs five distinct
values or a history of twelve events would be missed. When a bound matters,
raise it and watch the state count: `CancelAfter` goes from 33 863 states to
several hundred thousand by adding two frames and one value. TLC handles
millions of states in minutes; beyond that, Apalache (a symbolic checker
for TLA+) can sometimes prove a property for all sizes where TLC can only
enumerate.

**It is stricter than the JavaScript event loop.** TLC explores every
interleaving of enabled actions. The real scheduler orders same-frame work
deterministically, and synchronous code is never interrupted. So TLC can
report a race that cannot happen in practice. That is usually the right
side to err on: an operator correct under all interleavings is correct
under the real one. When a false race is reported, the fix is to add the
scheduler's rule to the model (for example, that the source cannot deliver
between `Fire` and the end of its frame), not to weaken the property.

**Liveness is expensive and subtle.** Liveness checking searches for
cycles; it is slower, limited to smaller models, and its counterexamples
are harder to read. Lamport's own material puts safety first and liveness
last for these reasons. The specs here follow that: every operator has
safety invariants; deadline-style requirements are written as invariants
over `now`; full liveness is reserved for the operators that can hang
(`combineLatest`, `concatMap`, and by extension `forkJoin`, `zip`, `last`,
`toArray`).

## 7. On tla-ts

tla-ts is young (version 0.0.3, a single maintainer) and a wrong "pass"
from a model checker is the worst failure it can have. What this session
established:

- One naming difference: a violated action property, `[][A]_vars`, is
  reported by TLC as "Action property X is violated" and by the tla-ts
  `check()` API as status `liveness-violation` (its CLI prints TLC's
  wording and exits with 13). `scripts/check.mjs` accepts either for a
  manifest entry expecting `property-violation`.
- On these sixty-three configurations, tla-ts and TLC agree on every outcome,
  every violated property, and every state count of a complete run,
  including the three `Share` models of several hundred thousand states.
- It handled everything the specs use: `EXTENDS` of a local module, model
  values, string constants, records, `RECURSIVE`, `LAMBDA`, `CASE`,
  action properties, `WF_vars`, `~>`, and `\A` over a temporal formula.
- It runs from Node with no Java, and its `check()` API returns status,
  counts and the counterexample trace as data.

The sensible division of labour: TLC is the authority for any claim that
matters; tla-ts is the convenience layer for CI, for turning traces into
marble tests, and for anything that must run in a browser. `check:both`
runs the manifest through both and is the cheapest possible guard against
the two ever disagreeing.

## 8. Suggested workflow

1. **Write the spec from the documentation, before or alongside the
   operator.** The variables are the streams plus the operator's private
   state; the actions are its reactions; the invariants are the
   documentation's sentences.
2. **Check safety first.** Invariants and the `ObservableContract` action
   property. Fix the spec until it passes with small bounds.
3. **Break a guard and read the trace.** If removing a guard does not
   produce a counterexample, the properties are too weak.
4. **Turn deadlines into invariants over `now`.** Keep liveness for the
   operators that can hang, and state the fairness assumption explicitly.
5. **Run the invariants against the real operator** as property tests.
6. **Compose.** Chain the specs into the pipeline under design and check
   the end-to-end properties that span asynchronous boundaries.
